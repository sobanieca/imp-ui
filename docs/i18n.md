# imp-ui — Translations

Every imp app is translatable by default. Your translations are plain JavaScript files you write,
`t('some.key')` looks a message up in them, and the current language is the one thing the web
already has a place for: the `lang` attribute on `<html>`. There is no i18n library to install, no
message format to compile, and no store to configure.

You declare which translations your app has — in `init` for the app, in `area` for a lazily loaded
section — and imp loads the right ones at the right time. Three names do everything else:

```js
import { init } from 'imp'
import { lang, setLang, t } from 'imp/i18n'
```

## Translations are a file

Write your messages as an ordinary module whose default export is a plain object:

```js
// locales/en.js
export default {
  todo: {
    title: 'Todos',
    greeting: 'Hi, {name}',
    remaining: '{total} left',
  },
}
```

```js
// locales/pl.js
export default {
  todo: {
    title: 'Zadania',
    greeting: 'Cześć, {name}',
    remaining: 'Pozostało: {total}',
  },
}
```

Keys and strings, nothing else. Nest the groups however suits your app — the shape is yours, and
`t()` addresses a message by its dotted path (`todo.title`). Because a translation file is just a
module, you can split it across files, import one lazily, or build one at runtime like any other
value.

## Setting the app up — `init`

At your entry point, tell imp what the app is configured with. `init` applies the theme and loads
the translations for the starting language before you mount, so the first paint is already
translated:

```js
import { init, mount } from 'imp'

await init({
  theme: 'imp-light',
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})

mount('#app', app())
```

`translations` is a **map of language code to loader**, not a bag of messages. imp calls exactly one
of them: the loader for the language the app starts in. The other languages are never downloaded
until someone asks for them, so an app that speaks twelve languages ships one.

A loader is a function that `import()`s the file — nothing more. The bundler gives each one its own
chunk with no configuration, the browser downloads it the moment imp calls for it, and the module's
`default` export is unwrapped for you.

`init` takes three options, all optional:

| Option         | What it does                                                                      |
| -------------- | --------------------------------------------------------------------------------- |
| `theme`        | Applied with `applyTheme` — a built-in name or your own theme object.             |
| `translations` | Language code → loader. The starting language's messages load before `init` ends. |
| `lang`         | The language to start in. Defaults to `<html lang>`, then the browser's language. |

This is the only place an app declares its translations — there is no separate register call, and
nothing to keep in sync by hand.

## Looking a message up — `t`

```js
t('todo.title') // → 'Todos'
```

**Placeholders.** A `{name}` in a message is filled from a plain object of values:

```js
t('todo.greeting', { name: 'Ada' }) // → 'Hi, Ada'
```

Values are substituted as they are — a number goes in as `String(value)` — and a placeholder with no
matching value is left alone, so a typo shows up in the output instead of disappearing.

**A message is a string.** `t()` looks a key up and interpolates it; it does not choose between
variants. Number and date formatting, and picking the right wording for a count, are yours to do —
the platform's `Intl` is there when you need it:

```js
const total = new Intl.NumberFormat(lang.get()).format(1234.5)
t('todo.remaining', { total })
```

**A missing message never throws.** If a key is not registered in any language, `t()` returns the
key itself and warns once in the console, so a gap shows up as a visible, searchable string rather
than a crash.

## The current language — `<html lang>`

The language your app is in is the `lang` attribute on the `<html>` element — the same attribute
that already tells browsers how to hyphenate text, which dictionary to spell-check against, and how
a screen reader should pronounce your page. imp reads it rather than keeping a language of its own:

```js
await setLang('pl')
```

`setLang` is async because switching language means loading that language's messages first. It loads
everything the app currently needs — the app's own translations from `init`, plus those of the area
you are in — and only then writes `<html lang="pl">` and swaps the messages over. Nothing is ever
shown untranslated mid-switch, and the previous language's messages are released in the same step.

Setting the attribute yourself works too — imp notices, loads that language, and swaps it in a
moment later:

```js
document.documentElement.lang = 'pl'
```

If you never set it at all, imp uses the visitor's browser language, so declaring your translations
is enough to serve people in their own language.

**Which language a message comes from.** A regional language loads its base language too, and its
own messages shadow them: declare both `en` and `en-GB`, and `en-GB` can be three overrides rather
than a full copy. A language you have not translated falls back to the first one you declared.

Note what this does **not** do: only the active language is in memory, so a key missing from it
cannot fall back to another language's text — it shows the key. Every language you declare should
carry the messages your app actually asks for.

## Switching language

There are two ways to do it, and the simple one is fine for most apps.

**Reload the page.** Remember the choice, reload, and let `init` start the app in that language.
Nothing in your UI has to be reactive, because everything is built once, in the right language:

```js
const chooseLanguage = (code) => {
  localStorage.setItem('lang', code)
  location.reload()
}

// entry point
await init({
  lang: localStorage.getItem('lang') ?? undefined,
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})
```

**Or switch in place.** `lang` is a read-only state, exactly like `theme`. Bind a text node to it
and the text re-localizes the moment the language changes — imp updates that one text node, nothing
re-renders and nothing reloads:

```js
import { component } from 'imp'
import { button, div, h1 } from 'imp/html'
import { lang, setLang, t } from 'imp/i18n'

export const header = component('app-header', {
  onMount: () =>
    div(
      h1(lang.text(() => t('todo.title'))),
      button({ events: { click: () => setLang('pl') } }, 'Polski'),
    ),
})
```

For a translated **prop** — a label, a title, a placeholder — derive it from `lang` with `computed`
and pass that; the attribute updates on its own when the language changes:

```js
import { computed } from 'imp/state'

button({ 'aria-label': computed([lang], () => t('todo.add')) }, '+')
```

You can also react to a language change directly:

```js
lang.watch((code) => console.log('now showing', code))
```

The standard components follow the same rule: every string they show is bound through `lang`, so
they re-localize in place on a language switch without a reload. Do the same in your own components
— `lang.text(() => t('key'))` rather than a bare `t('key')` — and switching in place stays an option
you can add later without rewriting screens.

## Translations for lazy-loaded areas

A route **area** (see **[Routing](routing.md)**) is a section of the app the browser downloads the
first time someone navigates into it. Its messages belong to it, and an area declares them the same
way the root app does — as a map of language to loader:

```js
// admin/area.js
import { area } from 'imp/router'

export default area({
  routes: {
    '/': () => dashboard(),
    '/users': () => users(),
  },
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})
```

```js
// app.js
router({
  routes: {
    '/': () => home(),
    '/admin': area(() => import('./admin/area.js')),
  },
})
```

You never call anything to make this work. Entering `/admin` loads the area's chunk **and** the one
translation file matching the language the app is currently in, before the first screen of the area
paints. Navigating between screens inside the area keeps it loaded. Leaving the area drops it. And
switching language while inside the area loads the area's messages for the new language alongside
the app's, so both change together.

**Namespace each area's messages under its own key** (`admin.users.title`, not `title`). All
messages share one namespace, and the ones loaded last win on a colliding key — which is what you
want when an area deliberately overrides a message the app defines, and not what you want when two
areas both happen to claim `title`. Nesting each area's messages under its own top-level key keeps
them from ever meeting.

**What "dropped" means.** Leaving an area, or switching language, drops imp's reference to the
messages it no longer needs, and they stop resolving — `t('admin.title')` outside the admin area
gives you back the key. What it does not do is shrink the heap: a module the browser has loaded
stays in its registry for the life of the page, and no framework can evict one. The same note in
**[Routing](routing.md)** about an area's code applies to its messages.

What you get from all this, then, is **what you download**, not what you hold: a visitor who never
opens the admin section never downloads its messages, and a visitor reading in Polish never
downloads English. Dropping keeps lookups honest — an area's keys stop resolving once you leave it,
so a missing message shows up while you are developing rather than silently resolving to some other
section's text.

**What to watch out for once messages can disappear.** `t()` returns the key for a message it cannot
find, and never throws. Anything that outlives an area — a header, a breadcrumb, a toast queue —
should read from the app's own messages, not an area's; a node bound with `lang.text(…)` that
survives its area would start rendering raw keys.

## Testing translated text

Translated text is ordinary text, so nothing special is needed. Call `init` once at the top of the
test file, switch languages with `setLang`, and assert on what renders:

```js
import { init } from 'imp'
import { setLang, t } from 'imp/i18n'
import { beforeAll, expect, test } from 'imp/test'

beforeAll(() =>
  init({
    translations: {
      en: () => import('./locales/en.js'),
      pl: () => import('./locales/pl.js'),
    },
  })
)

test('greets in the active language', async () => {
  await setLang('pl')
  expect(t('greet')).toEqual('Cześć')
})
```

Remember to `await setLang` — it loads that language before it switches.
