# imp-ui - Translations

Every imp app is translatable by default. Your translations are plain JavaScript files that you
write. `t('some.key')` finds a message in them. The current language is the one thing that the web
already has a place for: the `lang` attribute on `<html>`. There is no i18n library to install, no
message format to compile, and no store to configure. The text direction follows the language on its
own.

You declare which translations your app has. You do this in `init` for the app, and in `area` for a
section that loads lazily. imp then loads the correct translations at the correct time. A small set
of names does everything else:

```js
import { init } from 'imp'
import { defaultMessages, dir, lang, missingMessages, setLang, t } from 'imp/i18n'
```

## A translation is a file

Write your messages as an ordinary module. Its default export is a plain object:

```js
// locales/en.js
export default {
  todo: {
    title: 'Todos',
    greeting: 'Hi, {name}',
    remaining: '{total} left',
  },
}
```

```js
// locales/pl.js
export default {
  todo: {
    title: 'Zadania',
    greeting: 'Cześć, {name}',
    remaining: 'Pozostało: {total}',
  },
}
```

The file holds keys and strings, nothing else. Nest the groups in the way that suits your app. The
shape is yours. `t()` addresses a message by its dotted path, such as `todo.title`. A translation
file is a module. So you can split it across files, import one lazily, or build one at runtime, like
any other value.

## How to set the app up - `init`

At your entry point, tell imp how the app is configured. `init` applies the theme and loads the
translations of the starting language before you mount. So the first paint is already translated:

```js
import { init, mount } from 'imp'

await init({
  theme: 'imp-light',
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})

mount('#app', app())
```

`translations` is a **map of language code to loader**. It is not a set of messages. imp calls
exactly one loader: the loader of the language that the app starts in. The browser never downloads
another language until somebody asks for it. So an app that speaks twelve languages ships one.

A loader is a function that calls `import()` on the file, and nothing more. The bundler gives each
loader its own chunk, with no configuration. The browser downloads the chunk the moment when imp
calls for it. imp unwraps the `default` export of the module for you.

`init` takes four options, and all of them are optional:

| Option         | What it does                                                                       |
| -------------- | ---------------------------------------------------------------------------------- |
| `theme`        | Applied with `applyTheme` - a built-in name or your own theme object.              |
| `translations` | Language code -> loader. The starting language's messages load before `init` ends. |
| `lang`         | The language to start in. Defaults to `<html lang>`, then the browser's language.  |
| `dir`          | Pins the text direction. Left out, it follows the language - see below.            |

This is the only place where an app declares its translations. There is no separate register call,
and there is nothing to keep in step by hand.

## How to look a message up - `t`

```js
t('todo.title') // -> 'Todos'
```

**Placeholders.** imp fills a `{name}` in a message from a plain object of values:

```js
t('todo.greeting', { name: 'Ada' }) // -> 'Hi, Ada'
```

imp substitutes a value as it is, and a number goes in as `String(value)`. imp leaves a placeholder
with no matching value as it is. So a spelling mistake appears in the output instead of
disappearing.

**A message is a string.** `t()` looks a key up and interpolates it. It does not choose between
variants. You format a number and a date yourself, and you pick the correct wording for a count. The
`Intl` object of the platform is there when you need it:

```js
const total = new Intl.NumberFormat(lang.get()).format(1234.5)
t('todo.remaining', { total })
```

**A missing message never throws.** When no language registers a key, `t()` returns the key itself
and warns once in the console. So a gap appears as a visible string that you can search for, not as
a crash. A key with **default wording** shows that wording instead. The standard components read
such keys, and your own components can declare them. The next section covers this.

## The words that a component brings with it

Some text on the screen is not yours to write. Examples are the **No results** of an empty table,
the **Cancel** of a dialog, and the **Loading...** of a spinner. This works exactly as
[design tokens](theming.md) work. A component reads its colours from
`var(--imp-color-text, #0f172a)`. That is the value of your theme when you defined one, and a
built-in fallback when you did not. Its words follow the same shape. imp finds them under an `imp.`
key, and falls back to the English wording of the component. So an app with no translation file
still reads correctly:

```js
emptyState() // -> "Nothing here yet"
```

**Your translation wins.** Write the key in your own translation files, and the component uses your
words:

```js
// locales/pl.js
export default {
  imp: { state: { empty: 'Nic tu jeszcze nie ma' } },
}
```

That is the whole rule. It applies per key and per language, like an override of a single token.
Translate `imp.state.empty` in Polish only. A Polish reader then sees your wording, and every other
language keeps the English of the component. To add a language, you never have to fill in a list of
framework strings first. You can override only the keys whose tone you want to own. Is it _Delete_
or _Remove_? Is it _OK_ or _Got it_?

imp interpolates default wording like any other message. So a key with a `{placeholder}` works the
same way, whether it comes from your files or from the component.

**How to check your coverage.** To learn which of these keys your current language does not
translate yet, call `missingMessages()`. It returns an empty array when you covered them all:

```js
import { missingMessages } from 'imp/i18n'

missingMessages() // -> ['imp.state.empty']
```

Nothing is broken while a key is on that list. The reader sees English. A component registers its
wording the first time when you render it. So render the screens that you care about before you ask.

## Default wording for your own components - `defaultMessages`

A component that you write can carry wording in the same way. That is what makes a shared component
library usable in an app that has not translated it yet:

```js
import { component } from 'imp'
import { div } from 'imp/html'
import { defaultMessages, lang, t } from 'imp/i18n'

const messages = {
  'billing.trialEnded': 'Your trial has ended',
  'billing.daysLeft': '{days} days left',
}

const definition = {
  setup: () => div(lang.text(() => t('billing.trialEnded'))),
}

let create = null

export const trialNotice = (...args) => {
  if (!create) {
    defaultMessages(messages)
    create = component('my-app-trial-notice', definition)
  }
  return create(...args)
}
```

`defaultMessages` takes a flat object that maps a **dotted key to wording**. Write the key exactly
as `t()` reads it, and the value as a plain string. Call the function where the component defines
itself, not at the top of the module. A module that nobody renders then has no side effect.

Everything else follows the rules above. A translation of the same key shadows the wording, and imp
fills a `{placeholder}` in both cases.

## The current language - `<html lang>`

The language of your app is the `lang` attribute on the `<html>` element. That is the same attribute
that already tells a browser how to hyphenate the text, which dictionary to check the spelling
against, and how a screen reader must pronounce your page. imp reads the attribute. It does not keep
a language of its own:

```js
await setLang('pl')
```

`setLang` is async, because a change of language first loads the messages of that language. It loads
everything that the app needs now. That is the translations of the app from `init`, and the
translations of the area that you are in. Only then does it write `<html lang="pl">` and swap the
messages. imp never shows untranslated text in the middle of a switch, and it releases the messages
of the previous language in the same step.

You can also set the attribute yourself. imp notices the change, loads that language, and swaps it
in a moment later:

```js
document.documentElement.lang = 'pl'
```

When you never set the attribute, imp uses the browser language of the visitor. So a declaration of
your translations is enough to serve a person in their own language.

**Which language a message comes from.** A regional language also loads its base language, and its
own messages shadow the base messages. Declare both `en` and `en-GB`, and `en-GB` can be three
overrides instead of a full copy. A language that you have not translated falls back to the first
language that you declared.

Note what this does **not** do. Only the active language is in memory. So a key that is missing from
it cannot fall back to the text of another language. It shows the key, or the default wording when
the key has any. Every language that you declare must carry the messages that your app asks for.

## Text direction - `<html dir>`

Some languages read from right to left. imp treats the direction as it treats the language. The
platform already has the attribute for it. So imp keeps `<html dir>` in step with `<html lang>`, and
invents nothing.

You write nothing. `init` sets the direction for the language that the app starts in, and every
change of language moves it:

```js
await setLang('ar') // <html lang="ar" dir="rtl">
await setLang('en') // <html lang="en" dir="ltr">
```

The starting language defaults to the browser language of the visitor. So an app that declares
Arabic or Hebrew translations, and never calls `setLang`, already lays out from right to left for
the people who read in those languages.

The direction comes from the **script**, not from a list of languages. So imp handles a language
that uses more than one alphabet correctly. `az-Arab` is right to left, and `az-Latn` is left to
right. A regional code such as `fa-IR` follows its base language.

**How to read the direction - `dir`.** `dir` is a read-only state with the same shape as `lang` and
`theme`. So you can bind to it wherever the direction matters:

```js
dir.get() // -> 'rtl'
dir.watch(self, (direction) => ...)
div(dir.text((direction) => direction === 'rtl' ? '<-' : '->'))
```

`dir` changes only when the language changes. So a binding to `dir` costs nothing on a page that
never changes language.

**Write your CSS in logical properties.** The attribute is the small half of the work. The rest is
to make your styles follow it. Use `margin-inline-start` in place of `margin-left`. Use
`padding-inline-end` in place of `padding-right`. Use `inset-inline-start` in place of `left`. Use
`text-align: start` and `text-align: end` in place of `left` and `right`. Each one of those follows
the direction on its own. So one stylesheet serves both directions, and every standard component is
already written this way. A physical property is the only thing that does not follow the attribute.

**The layout components follow the direction too.** `flex` and `stack` take
`horizontalAlign: 'start'` and `'end'`, not `'left'` and `'right'`. A row lays its children out from
the edge where the language starts. So a header that you write once reads correctly in English and
in Arabic, with no `dir` branch and no reversed child list. Design your screens in `start` and `end`
from the beginning, and right-to-left support costs you nothing later.

**How to pin the direction.** A screen whose direction must not follow the language pins it.
Examples are a code editor, a terminal view and a column of file paths:

```js
await init({ dir: 'ltr' })
```

A pinned direction wins against the language for as long as the app runs. To pin one _part_ of a
page, and not the whole app, put `dir` on that element. It is an ordinary HTML attribute:

```js
pre({ dir: 'ltr' }, sourceCode)
```

**Text that you did not write.** A comment typed in Arabic inside a page that is otherwise English
is a different problem. The direction depends on the text, not on the app. The platform solves it.
Give the element that holds the text `dir: 'auto'`. The browser then takes the direction from the
first strongly directional character in the content:

```js
p({ dir: 'auto' }, comment.body)
```

Use this on anything that a user typed. Leave the rest to `<html dir>`.

**Before the first paint.** imp sets the attribute in `init`, which runs before your app mounts. So
imp never lays out what it renders in the wrong direction. The browser lays out the content of your
`index.html` before any of that. So when the shell has visible markup, put the direction on it. An
app in one language can write `<html lang="ar" dir="rtl">`, and imp agrees with it.

## How to change the language

There are two ways, and the simple one suits most apps.

**Reload the page.** Store the choice, reload, and let `init` start the app in that language.
Nothing in your UI must be reactive, because imp builds everything once, in the correct language:

```js
const chooseLanguage = (code) => {
  localStorage.setItem('lang', code)
  location.reload()
}

// entry point
await init({
  lang: localStorage.getItem('lang') ?? undefined,
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})
```

**Or change the language in place.** `lang` is a read-only state, exactly like `theme`. Bind a text
node to it. The text localizes again the moment when the language changes. imp updates that one text
node. Nothing renders again, and nothing reloads:

```js
import { component } from 'imp'
import { button, div, h1 } from 'imp/html'
import { lang, setLang, t } from 'imp/i18n'

export const header = component('app-header', {
  setup: () =>
    div(
      h1(lang.text(() => t('todo.title'))),
      button({ events: { click: () => setLang('pl') } }, 'Polski'),
    ),
})
```

For a translated **prop**, such as a label, a title or a placeholder, derive the value from `lang`
with `computed` and pass that. The attribute then updates on its own when the language changes:

```js
import { computed } from 'imp/state'

button({ 'aria-label': computed([lang], () => t('todo.add')) }, '+')
```

You can also react to a change of language directly:

```js
lang.watch(self, (code) => console.log('now showing', code))
```

The standard components follow the same rule. Every string that they show is bound through `lang`.
So they localize again in place on a change of language, with no reload. Do the same in your own
components. Write `lang.text(() => t('key'))`, not a bare `t('key')`. A change in place then stays
an option that you can add later, and you do not rewrite the screens.

## The words of the application map

The nav, the breadcrumb trail, the document title and the placeholder of an unbound node take their
words from the application map, see **[Routing](routing.md)**. You translate them in the same files
as the rest of the app, under the key `appMap`. The rest of the key is the id of the node, then
`label`, `group` or `description`:

```js
// locales/pl.js
export default {
  appMap: {
    projects: { label: 'Projekty' },
    admin: {
      label: 'Administracja',
      users: { label: 'Uzytkownicy', group: 'Konta', description: 'Kazdy, kto ma login' },
    },
  },
}
```

A message wins over the `label`, `group` or `description` that the map writes, and over the name of
the node. When no message exists, the map's own words show. So an app in one language writes no
message at all, and the map file never calls `t()`.

Put these keys in the translations of the app, not in the translations of an area. A section row in
the nav shows before the code of its area has loaded, so the message must be in memory from the
start.

## Translations for a lazily loaded area

A route **area**, see **[Routing](routing.md)**, is a section of the app that the browser downloads
the first time when somebody navigates into it. Its messages belong to it. An area declares them the
same way as the root app, as a map of language to loader:

```js
// admin/area.js
import { area } from 'imp/router'
import { app } from '../app-map.js'

export default area({
  screens: {
    [app.admin]: () => dashboard(),
    [app.admin.users]: () => users(),
  },
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})
```

```js
// main.js
router({
  map: app,
  screens: {
    [app.home]: () => home(),
    [app.admin]: area(() => import('./admin/area.js')),
  },
})
```

You call nothing to make this work. An entry to `/admin` loads the chunk of the area **and** the one
translation file that matches the current language of the app, before the first screen of the area
paints. A navigation between the screens inside the area keeps it loaded. An exit from the area
drops it. A change of language while you are inside the area loads the messages of the area for the
new language, with the messages of the app. So both change together.

**Put the messages of each area under its own key**, such as `admin.users.title`, not `title`. All
messages share one namespace, and on a collision the last loaded key wins. That is what you want
when an area overrides a message of the app on purpose. It is not what you want when two areas both
claim `title`. When you nest the messages of each area under its own top-level key, the two never
meet.

**What "dropped" means.** When you leave an area, or change the language, imp drops its reference to
the messages that it no longer needs, and those messages stop resolving. Outside the admin area,
`t('admin.title')` gives you back the key. What this does not do is make the heap smaller. A module
that the browser has loaded stays in its registry for the life of the page, and no framework can
remove it. The same note in **[Routing](routing.md)** about the code of an area applies to its
messages.

So what you gain is about **what you download**, not about what you hold. A visitor who never opens
the admin section never downloads its messages. A visitor who reads in Polish never downloads
English. The drop also keeps the lookups honest. The keys of an area stop resolving when you leave
it. So a missing message appears while you develop, instead of resolving to the text of another
section.

**What to watch for when a message can disappear.** `t()` returns the key for a message that it
cannot find, or the default wording when the key has any, and it never throws. Anything that lives
longer than an area must read from the messages of the app, not from the messages of an area. A
header, a breadcrumb trail and a toast queue are examples. A node that is bound with
`lang.text(...)`, and that outlives its area, starts to render raw keys.

## How to test translated text

Translated text is ordinary text, so you need nothing special. Call `init` once at the top of the
test file, change the language with `setLang`, and assert on what renders:

```js
import { init } from 'imp'
import { setLang, t } from 'imp/i18n'
import { beforeAll, expect, test } from 'imp/test'

beforeAll(() =>
  init({
    translations: {
      en: () => import('./locales/en.js'),
      pl: () => import('./locales/pl.js'),
    },
  })
)

test('greets in the active language', async () => {
  await setLang('pl')
  expect(t('greet')).toEqual('Cześć')
})
```

Remember to `await setLang`. It loads the language before it changes it.
