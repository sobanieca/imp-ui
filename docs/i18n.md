# imp-ui - Translations

Every imp app is translatable by default. Your translations are plain JavaScript files that you
write. `t('some.key')` finds a message in them. The current language is the `lang` attribute on
`<html>`, the same place the browser already uses. There is no i18n library to install, no message
format to compile, and no store to configure. The text direction follows the language on its own.

You declare which translations your app has. Do this in `init` for the app, and in `area` for a
section that loads lazily. imp then loads the correct translations at the correct time. A small set
of names does everything else:

```js
import { init } from 'imp'
import { defaultMessages, dir, lang, missingMessages, setLang, t } from 'imp/i18n'
```

## A translation is a file

Write your messages as an ordinary module. Its default export is a plain object:

```js
// locales/en.js
export default {
  todo: {
    title: 'Todos',
    greeting: 'Hi, {name}',
    remaining: '{total} left',
  },
}
```

```js
// locales/pl.js
export default {
  todo: {
    title: 'Zadania',
    greeting: 'Czesc, {name}',
    remaining: 'Pozostalo: {total}',
  },
}
```

The file holds keys and strings, nothing else. Nest the groups in the way that suits your app. The
shape is yours. `t()` addresses a message by its dotted path, such as `todo.title`. A translation
file is an ordinary module, so you can split it across files, import one lazily, or build one at
runtime.

## Set up the app - `init`

At your entry point, tell imp how the app is configured. `init` applies the theme and loads the
translations of the starting language before you mount, so the first paint is already translated:

```js
import { init, mount } from 'imp'

await init({
  theme: 'imp-light',
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})

mount('#app', app())
```

`translations` is a map of language code to loader, not a set of messages. imp calls only the loader
of the language the app starts in. The browser does not download another language until someone asks
for it. So an app that speaks twelve languages ships one.

A loader is a function that calls `import()` on the file. The bundler gives each loader its own
chunk. The browser downloads the chunk when imp calls for it. imp unwraps the `default` export of
the module for you.

`init` takes four options. All of them are optional.

| Option         | What it does                                                                       |
| -------------- | ---------------------------------------------------------------------------------- |
| `theme`        | Applied with `applyTheme` - a built-in name or your own theme object.              |
| `translations` | Language code -> loader. The starting language's messages load before `init` ends. |
| `lang`         | The language to start in. Defaults to `<html lang>`, then the browser's language.  |
| `dir`          | Pins the text direction. Left out, it follows the language - see below.            |

This is the only place where an app declares its translations. There is no separate register call.

## Look up a message - `t`

```js
t('todo.title') // -> 'Todos'
```

**Placeholders.** imp fills a `{name}` in a message from a plain object of values:

```js
t('todo.greeting', { name: 'Ada' }) // -> 'Hi, Ada'
```

imp inserts a value as it is, and turns a number into a string. imp leaves a placeholder with no
matching value as it is, so a spelling mistake shows up in the output instead of disappearing.

**A message is a string.** `t()` looks up a key and fills its placeholders. It does not choose
between variants. Format a number and a date yourself, and pick the correct wording for a count. Use
the platform's `Intl` object for this:

```js
const total = new Intl.NumberFormat(lang.get()).format(1234.5)
t('todo.remaining', { total })
```

**A missing message never throws.** When no language has a key, `t()` returns the key itself and
warns once in the console. A gap then shows as a visible string you can search for, not as a crash.
A key with default wording shows that wording instead. Standard components read such keys, and your
own components can declare them too. See the next section.

## The words that a component brings with it

Some text on the screen is not yours to write. Examples are the **No results** of an empty table,
the **Cancel** of a dialog, and the **Loading...** of a spinner. This works like
[design tokens](theming.md) work. A component reads its colors from a token that falls back to a
built-in value when your theme does not set it. Component words follow the same pattern. imp looks
for them under an `imp.` key, and falls back to the English wording of the component. So an app with
no translation file still reads correctly:

```js
emptyState() // -> "Nothing here yet"
```

**Your translation wins.** Write the key in your own translation files, and the component uses your
words:

```js
// locales/pl.js
export default {
  imp: { state: { empty: 'Nic tu jeszcze nie ma' } },
}
```

That is the whole rule. It applies per key and per language. Translate `imp.state.empty` in Polish
only, and a Polish reader sees your wording while every other language keeps the component's
English. To add a language, you do not need to fill in a list of framework strings first. Override
only the keys whose wording you want to change.

**Check your coverage.** To learn which of these keys your current language does not translate yet,
call `missingMessages()`. It returns an empty array when you have covered them all:

```js
import { missingMessages } from 'imp/i18n'

missingMessages() // -> ['imp.state.empty']
```

Nothing is broken while a key is on that list. The reader sees English. A component registers its
wording the first time you render it, so render the screens you care about before you check.

## Default wording for your own components - `defaultMessages`

A component you write can carry wording the same way. This makes a shared component library usable
in an app that has not translated it yet:

```js
import { component } from 'imp'
import { div } from 'imp/html'
import { defaultMessages, lang, t } from 'imp/i18n'

const messages = {
  'billing.trialEnded': 'Your trial has ended',
  'billing.daysLeft': '{days} days left',
}

const definition = {
  setup: () => div(lang.text(() => t('billing.trialEnded'))),
}

let create = null

export const trialNotice = (...args) => {
  if (!create) {
    defaultMessages(messages)
    create = component('my-app-trial-notice', definition)
  }
  return create(...args)
}
```

`defaultMessages` takes a flat object that maps a dotted key to wording. Write the key exactly as
`t()` reads it, and the value as a plain string. Call the function where the component defines
itself, not at the top of the module, so a module nobody renders has no side effect.

Everything else follows the rules above. A translation of the same key overrides the wording, and
imp fills a `{placeholder}` in both cases.

## The current language - `<html lang>`

The language of your app is the `lang` attribute on the `<html>` element. This is the same attribute
that tells a browser how to hyphenate text, which dictionary to check spelling against, and how a
screen reader must pronounce your page. imp reads the attribute and keeps no language of its own:

```js
await setLang('pl')
```

`setLang` is async because a change of language first loads the messages of that language. It loads
the translations of the app from `init`, and the translations of the area you are in. Only then does
it write `<html lang="pl">` and swap the messages. imp never shows untranslated text during a
switch, and it releases the messages of the previous language at the same time.

You can also set the attribute yourself. imp notices the change, loads that language, and swaps it
in a moment:

```js
document.documentElement.lang = 'pl'
```

When you never set the attribute, imp uses the visitor's browser language. So declaring your
translations is enough to serve a person in their own language.

**Which language a message comes from.** A regional language also loads its base language, and its
own messages override the base messages. Declare both `en` and `en-GB`, and `en-GB` can hold just
three overrides instead of a full copy. A language you have not translated falls back to the first
language you declared.

Note what this does **not** do. Only the active language is in memory, so a key missing from it
cannot fall back to the text of another language. It shows the key, or the default wording when the
key has any. Every language you declare must carry the messages your app needs.

## Text direction - `<html dir>`

Some languages read from right to left. imp treats the direction the way it treats the language: the
platform already has an attribute for it, `<html dir>`, and imp keeps it in step with `<html lang>`.

You write nothing. `init` sets the direction for the language the app starts in, and every change of
language updates it:

```js
await setLang('ar') // <html lang="ar" dir="rtl">
await setLang('en') // <html lang="en" dir="ltr">
```

The starting language defaults to the visitor's browser language. So an app that declares Arabic or
Hebrew translations, and never calls `setLang`, already lays out right to left for readers of those
languages.

The direction comes from the script, not from a list of languages. imp handles a language that uses
more than one alphabet correctly: `az-Arab` is right to left, and `az-Latn` is left to right. A
regional code such as `fa-IR` follows its base language.

**Read the direction - `dir`.** `dir` is a read-only state with the same shape as `lang` and
`theme`, so you can bind to it wherever the direction matters:

```js
dir.get() // -> 'rtl'
dir.watch(self, (direction) => ...)
div(dir.text((direction) => direction === 'rtl' ? '<-' : '->'))
```

`dir` changes only when the language changes, so a binding to `dir` costs nothing on a page that
never changes language.

**Write your CSS in logical properties.** The attribute is the small half of the work. The rest is
making your styles follow it. Use `margin-inline-start` instead of `margin-left`. Use
`padding-inline-end` instead of `padding-right`. Use `inset-inline-start` instead of `left`. Use
`text-align: start` and `text-align: end` instead of `left` and `right`. Each of these follows the
direction on its own, so one stylesheet serves both directions. Every standard component already
uses this pattern. A physical property is the only kind that ignores the attribute.

**The layout components follow the direction too.** `flex` and `stack` take
`horizontalAlign: 'start'` and `'end'`, not `'left'` and `'right'`. A row lays its children out from
the edge where the language starts. So a header you write once reads correctly in English and in
Arabic, with no `dir` branch and no reversed child list. Design your screens in `start` and `end`
from the beginning, and right-to-left support costs you nothing later.

**Pin the direction.** A screen whose direction must not follow the language pins it. Examples are a
code editor, a terminal view and a column of file paths:

```js
await init({ dir: 'ltr' })
```

A pinned direction wins against the language for as long as the app runs. To pin one part of a page,
not the whole app, put `dir` on that element. It is an ordinary HTML attribute:

```js
pre({ dir: 'ltr' }, sourceCode)
```

**Text that you did not write.** A comment typed in Arabic inside an otherwise English page is a
different problem: the direction depends on the text, not on the app. The platform solves it. Give
the element that holds the text `dir: 'auto'`. The browser then takes the direction from the first
strongly directional character in the content:

```js
p({ dir: 'auto' }, comment.body)
```

Use this on anything a user typed. Leave the rest to `<html dir>`.

**Before the first paint.** imp sets the attribute in `init`, which runs before your app mounts, so
imp never lays out its content in the wrong direction. The browser lays out your `index.html` shell
before that. If your shell has visible markup, put the direction on it directly. An app in one
language can write `<html lang="ar" dir="rtl">`, and imp agrees with it.

## Change the language

There are two ways to do this. The simple one suits most apps.

**Reload the page.** Store the choice, reload, and let `init` start the app in that language.
Nothing in your UI must be reactive, because imp builds everything once, in the correct language:

```js
const chooseLanguage = (code) => {
  localStorage.setItem('lang', code)
  location.reload()
}

// entry point
await init({
  lang: localStorage.getItem('lang') ?? undefined,
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})
```

**Or change the language in place.** `lang` is a read-only state, like `theme`. Bind a text node to
it. The text localizes again the moment the language changes, and imp updates only that text node.
Nothing renders again, and nothing reloads:

```js
import { component } from 'imp'
import { button, div, h1 } from 'imp/html'
import { lang, setLang, t } from 'imp/i18n'

export const header = component('app-header', {
  setup: () =>
    div(
      h1(lang.text(() => t('todo.title'))),
      button({ events: { click: () => setLang('pl') } }, 'Polski'),
    ),
})
```

For a translated prop, such as a label, a title or a placeholder, derive the value from `lang` with
`computed` and pass that. The attribute then updates on its own when the language changes:

```js
import { computed } from 'imp/state'

button({ 'aria-label': computed([lang], () => t('todo.add')) }, '+')
```

You can also react to a change of language directly:

```js
lang.watch(self, (code) => console.log('now showing', code))
```

The standard components follow the same rule: every string they show is bound through `lang`, so
they localize again in place on a change of language, with no reload. Do the same in your own
components. Write `lang.text(() => t('key'))`, not a bare `t('key')`. This keeps a change-in-place
as an option you can add later, without rewriting your screens.

## The words of the application map

The nav, the breadcrumb trail, the document title and the placeholder of an unbound node take their
words from the application map. See [Routing](routing.md). Translate them in the same files as the
rest of the app, under the key `appMap`. The rest of the key is the id of the node, then `label`,
`group` or `description`:

```js
// locales/pl.js
export default {
  appMap: {
    projects: { label: 'Projekty' },
    admin: {
      label: 'Administracja',
      users: { label: 'Uzytkownicy', group: 'Konta', description: 'Kazdy, kto ma login' },
    },
  },
}
```

A message wins over the `label`, `group` or `description` the map writes, and over the name of the
node. When no message exists, the map's own words show. So an app in one language writes no message
at all, and the map file never calls `t()`.

Put these keys in the translations of the app, not in the translations of an area. A section row in
the nav shows before the code of its area has loaded, so its message must already be in memory.

## Translations for a lazily loaded area

A route area, see [Routing](routing.md), is a section of the app the browser downloads the first
time someone navigates into it. Its messages belong to it. An area declares them the same way as the
root app, as a map of language to loader:

```js
// admin/area.js
import { area } from 'imp/router'
import { app } from '../app-map.js'

export default area({
  screens: {
    [app.admin]: () => dashboard(),
    [app.admin.users]: () => users(),
  },
  translations: {
    en: () => import('./locales/en.js'),
    pl: () => import('./locales/pl.js'),
  },
})
```

```js
// main.js
router({
  map: app,
  screens: {
    [app.home]: () => home(),
    [app.admin]: area(() => import('./admin/area.js')),
  },
})
```

You call nothing to make this work. Entering `/admin` loads the chunk of the area and the one
translation file that matches the app's current language, before the first screen of the area
paints. Moving between screens inside the area keeps it loaded. Leaving the area drops it. Changing
the language while inside the area loads the area's messages for the new language, along with the
app's messages, so both change together.

**Put the messages of each area under its own key**, such as `admin.users.title`, not `title`. All
messages share one namespace, and on a collision the last loaded key wins. That is what you want
when an area overrides a message of the app on purpose. It is not what you want when two areas both
claim `title`. Nest the messages of each area under its own top-level key, and the two never
collide.

**What "dropped" means.** When you leave an area, or change the language, imp drops its reference to
the messages it no longer needs, and those messages stop resolving. Outside the admin area,
`t('admin.title')` gives you back the key. This does not shrink the heap. A module the browser has
loaded stays in its registry for the life of the page. The same note in [Routing](routing.md) about
the code of an area applies to its messages.

So what you gain is about what you download, not about what you hold. A visitor who never opens the
admin section never downloads its messages. A visitor who reads in Polish never downloads English.
The drop also keeps lookups honest: the keys of an area stop resolving as soon as you leave it, so a
missing message appears while you develop, instead of resolving to the text of another section.

**Watch for messages that can disappear.** `t()` returns the key for a message it cannot find, or
the default wording when the key has any, and it never throws. Anything that lives longer than an
area must read from the messages of the app, not from the messages of an area. A header, a
breadcrumb trail and a toast queue are examples. A node bound with `lang.text(...)` that outlives
its area starts to render raw keys.

## Test translated text

Translated text is ordinary text, so you need nothing special. Call `init` once at the top of the
test file, change the language with `setLang`, and assert on what renders:

```js
import { init } from 'imp'
import { setLang, t } from 'imp/i18n'
import { beforeAll, expect, test } from 'imp/test'

beforeAll(() =>
  init({
    translations: {
      en: () => import('./locales/en.js'),
      pl: () => import('./locales/pl.js'),
    },
  })
)

test('greets in the active language', async () => {
  await setLang('pl')
  expect(t('greet')).toEqual('Czesc')
})
```

Always `await setLang`. It loads the language before it changes it.
