# `imp pwa` — progressive web app toolkit

Make imp aware that an app can ship as a PWA and give it a first-class toolkit for the boilerplate:
a generated web app manifest, scaled app icons from a single source image, and a production offline
service worker. Driven by an `imp pwa` command family plus a `pwa` block in `imp.json`.

## Not the dev service worker

imp already registers a service worker at `/@imp/sw.js`, but that is a **dev-only telemetry sink** —
it forwards browser network activity to the terminal and does no caching, so it gives no offline
capability (`cli/src/client.js`, `docs/cli.md` "Network telemetry"). PWA support is separate new
work: a real, cache-backed service worker shipped in the production build, plus the manifest and
icons the dev SW has nothing to do with. The dev telemetry SW stays as-is for `imp start`.

## Config — `pwa` block in `imp.json`

A single opt-in block describes the app; everything else is derived. Following the "hide Deno"
translation model, users only ever edit `imp.json`:

```json
{
  "pwa": {
    "name": "My App",
    "shortName": "App",
    "themeColor": "#0b0b0b",
    "backgroundColor": "#ffffff",
    "display": "standalone",
    "icon": "assets/icon.svg"
  }
}
```

- `icon` points at **one** high-resolution source image (SVG preferred, or a large PNG). imp scales
  it to every required target size — no hand-maintained icon set.
- Presence of `pwa` is what tells imp the app is a PWA; absent, nothing changes.
- `loadImpConfig` (`cli/src/config.js`) validates `pwa` as an object alongside
  `imports`/`fmt`/`lint`.

## Icon scaling — in-process

From the one source `icon`, generate the standard PWA icon set: `192×192`, `512×512`, a maskable
variant (with safe-zone padding), `apple-touch-icon` (180×180), and favicon sizes. Written into the
output the dev server and `imp bundle` serve.

Scaling must run **in-process** to honor `adr/in-process-toolchain.md` (no subprocess — so no
shelling out to ImageMagick/sharp CLIs). Resolve a pure-wasm or pure-JS image encoder/resizer,
vendored and pinned by checksum the same way the esbuild wasm module is (`cli/src/vendor`,
`adr/in-process-dependency-bundling.md`). SVG sources rasterize cleanly to each size; verify the
chosen library covers PNG decode + resize + encode. If no in-process path is viable, that constraint
belongs in the ADR discussion below before this is built.

## Manifest and head tags — derived, injected

- Derive a `manifest.webmanifest` from the `pwa` block plus the generated icon set.
- Extend the existing head-injection path (`buildHeadInjection` in `cli/src/start.js`, which already
  injects the import map and client script) to also emit `<link rel="manifest">`, the
  `<meta name="theme-color">` tag, and the `apple-touch-icon` links — so installability works in
  `imp start` with zero HTML edits, exactly like imp auto-injection today.
- `imp bundle` (`adr/production-bundling.md`) writes the manifest and icons as real files into the
  production output directory.

## Production service worker

The offline story is a real caching service worker generated at **build** time by `imp bundle`, not
the dev telemetry SW:

- Precache the built app shell (the entry files, hashed chunks, and assets `imp bundle` emits, the
  manifest, and the icons) so the app loads offline after first visit.
- Pick a default strategy (cache-first for hashed static assets, network-first for the HTML entry)
  with room to configure later.
- Register it from the production build only; in `imp start` the dev telemetry SW keeps its slot.

`imp bundle` exists (`adr/production-bundling.md`), so the offline SW can build on its output
directly; manifest + icon generation can still land against the dev server first and stand alone.

## Commands

- `imp pwa init` — scaffold the `pwa` block in `imp.json`, generate the icon set from the source
  image, and report what was written.
- `imp pwa icons` — (re)generate the icon set from the current `icon` source; run after changing the
  source art.
- `imp pwa check` — validate installability: a `pwa` block with required fields, a resolvable source
  icon, and a manifest that satisfies the install criteria (name, icons incl. 192 + 512, display,
  start_url). Exit non-zero on failure so it fits CI, mirroring `imp lint --check`.

## Docs

Document the `pwa` block, the `imp pwa` commands, the auto-injected manifest/icons in `imp start`,
and the generated offline service worker in `docs/cli.md` (and cross-link from the bundle docs).
Explain the dev-vs-production service worker distinction in plain language so readers are not
surprised that the dev SW does no caching.

## ADR impact

- Record a `pwa-toolkit.md` ADR (manifest + icons derived from a single `imp.json` block, one source
  icon scaled in-process, offline SW generated by `imp bundle`) and update the ADR table.
- If in-process image scaling forces any exception to `adr/in-process-toolchain.md`, capture it
  there the way `test-command.md` scopes its browser exception — but prefer a vendored wasm codec
  that keeps the no-subprocess guarantee intact.

## Open questions

- **Icon source format.** Require SVG for crisp rasterization at every size, or also accept a large
  PNG and downscale? Behavior when the source is smaller than a target size.
- **Maskable safe zone.** Padding ratio for the maskable icon so it survives platform masking.
- **SW caching strategy surface.** How much of the precache/runtime strategy to expose in `imp.json`
  versus keeping a single sensible default initially.
- **`start_url` / `scope`.** Derived defaults vs. explicit `pwa` fields, especially for apps served
  under a sub-path.
