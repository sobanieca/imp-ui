# Element-factory syntax, no JSX or templates

## Context

DOM structure has to be expressed somehow. The mainstream options are JSX (requires a
compile/transpile step), tagged-template HTML strings (`html\`<div>...\``, parsed at runtime), or
plain function calls. imp-ui is buildless by design — plain ES modules in the browser, no
transpilation ever — which rules JSX out immediately. Template strings keep buildlessness but
reintroduce a parser, a second (HTML-shaped) syntax to learn, and string-y interpolation that is
awkward to compose programmatically.

## Decision

DOM is expressed as **JavaScript function calls**:

- `el(tag, ...args)` is the single primitive.
- Per-tag shortcuts (`div`, `p`, `button`, … ~80 tags) are thin wrappers over `el`, generated from a
  tag list.
- Both are exported from the `imp/html` specifier (`library-import-namespaces.md`), which keeps the
  eighty-odd names out of the framework's own namespace.

No JSX, no string templates. UI helpers are just lowercase functions that call these factories and
return nodes; components with a lifecycle wrap the same calls (`web-component-lifecycle.md`).

## Consequences

- Zero build step; the same code that ships runs in the editor, tests, and browser unchanged.
- Composition is ordinary JavaScript — `map`, spread, conditionals, helper functions — with no
  template/expression boundary to cross.
- The tag-shortcut list is a fixed export surface; tags outside it use `el('tag', ...)`. Adding a
  shortcut is a one-line list edit.
- The trade-off is verbosity versus HTML-like markup, and an export surface of ~80 names in one
  specifier. Accepted: function calls are what agents generate most reliably and what composes
  without special-casing.
- Because shortcuts are generated by destructuring a map, every tag behaves identically to `el` —
  there is no per-tag special behavior to document.
